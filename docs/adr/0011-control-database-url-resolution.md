# ADR 0011: Control Database URL Resolution (`NENE_SUITE_CONTROL_DATABASE_URL`)

## Status

accepted

## Context

NeNe Suite's control database (`nene_suite`) stores the suite audit trail, install
session state, install manifests, and apex operator accounts. Two access points
must share the same connection parameters:

1. **`phinx.php`** — schema migrations run by the installer.
2. **`RuntimeServiceProvider`** — the HTTP runtime's `DatabaseQueryExecutorInterface`
   binding, used by all PDO repositories at request time.

Since the Phase 1 backend slices (Issue #28 onward), both access points delegate to
NENE2's `ConfigLoader`, which reads a NENE2-standard `.env` at the project root.
This worked during development but leaves a gap for the Tier B installer:

- The operator does not know which NENE2 env vars to set for the suite's own database.
- The binding terminology name (`NENE_SUITE_CONTROL_DATABASE_URL`, registered in
  `terminology.md` §12) is inconsistent with the runtime reading NENE2 config names.
- `audit-trail.md` §2 states the env var name but says "documented in installer ADR
  when implementation lands."
- ADR 0010 explicitly defers this as "a separate installer concern."

A second, separate connection (`NENE_SUITE_PROVISION_DB_*`) is used by
`PdoDatabaseProvisioner` to CREATE sibling app databases during provisioning.
That connection is **privileged** (root-level) and short-lived; it must not be
confused with the control DB connection, which is long-lived and unprivileged.

## Decision

### 1. URL format

`NENE_SUITE_CONTROL_DATABASE_URL` uses DSN URL format:

```
mysql://user:password@host:port/dbname
```

Example: `mysql://nene_suite:s3cret@db:3306/nene_suite`

This matches the format already accepted by Phinx's `url` environment key and is
consistent with `NENE_SUITE_PROVISION_DB_*` conventions.

> **Extended by [ADR 0016](0016-postgresql-control-and-provisioning-support.md):** the URL
> scheme also selects the engine — `pgsql://` (PostgreSQL) in addition to `mysql://`. The
> default port is inferred per engine when omitted (MySQL 3306, PostgreSQL 5432).

### 2. Resolution priority

Both `phinx.php` and `RuntimeServiceProvider` apply the same two-step resolver:

1. **If `NENE_SUITE_CONTROL_DATABASE_URL` is set** — parse it and construct the
   connection directly, bypassing NENE2's `ConfigLoader`.
2. **Otherwise** — fall back to NENE2's `ConfigLoader` (reads the project-root `.env`
   with NENE2's standard var names). This preserves existing dev/test behavior with
   no `.env` changes required.

The resolver is implemented as a single shared PHP class
(`NeNeSuite\Http\ControlDatabaseConfigResolver`) so the logic is never duplicated.

### 3. Installer responsibility (Tier B)

The Tier B Docker Compose installer **MUST** write `NENE_SUITE_CONTROL_DATABASE_URL`
into the suite's apex `.env` file before starting the PHP containers. It is the
installer's responsibility to:

- Generate the database name (`nene_suite` per `backend-standards.md §Repositories`).
- Generate a random unprivileged user credential for the control DB.
- Write the fully-formed DSN URL.

The installer uses the **separate** `NENE_SUITE_PROVISION_DB_*` credentials (root-level)
to `CREATE DATABASE nene_suite` and grant the unprivileged user access, then discards
the provisioner credentials.

### 4. Role separation: control DB vs provisioning DB

| Concern | Variable(s) | Privilege | Lifetime |
| --- | --- | --- | --- |
| Suite control DB (audit, sessions, manifests, operators) | `NENE_SUITE_CONTROL_DATABASE_URL` | Unprivileged (`nene_suite` user) | Long-lived (runtime) |
| Sibling DB creation | `NENE_SUITE_PROVISION_DB_HOST/PORT/USER/PASSWORD` | Root or equivalent | Installer only |

The provisioner connection is **never** used for the control DB tables, and the control
DB credentials are **never** used for `CREATE DATABASE` statements.

### 5. Secrets policy

The DSN URL contains a password. It:

- Is written to the apex `.env` file (not committed to git).
- Is **never** written to `suite_audit_events`, install manifests, or HTTP responses.
- Is **never** logged by any suite component.
- When suite env is regenerated by `WriteEnvConfigUseCase`, the output includes
  `NENE_SUITE_JWT_SECRET` (redacted) but does **not** include `NENE_SUITE_CONTROL_DATABASE_URL`
  — control DB credentials are not part of the suite env file written to sibling apps.

### 6. Dev / test fallback behavior

When `NENE_SUITE_CONTROL_DATABASE_URL` is not set, the resolver falls back to
NENE2's `ConfigLoader`. PHPUnit integration tests continue to use SQLite via NENE2's
standard env, requiring no changes to CI or test bootstrap.

## Consequences

**Benefits.**

- Operators configure one self-documenting variable for the suite's own database.
- Terminology, audit doc, backend-standards, and runtime are now consistent.
- Role separation between control DB and provisioner DB is formally documented.
- Dev/test requires no new environment setup.

**Costs.**

- `phinx.php` and `RuntimeServiceProvider` require a small refactor to use
  `ControlDatabaseConfigResolver` before the Tier B installer MVP ships.
- The Tier B installer must generate and write `NENE_SUITE_CONTROL_DATABASE_URL`
  as part of the provisioning step (after calling `ProvisionAppDatabasesUseCase`).

**Follow-up work.**

- Implement `ControlDatabaseConfigResolver` and update `phinx.php` +
  `RuntimeServiceProvider` (follow-up PR to this ADR).
- Tier B Docker Compose installer writes `NENE_SUITE_CONTROL_DATABASE_URL` during
  `database.provisioned` phase.
- Update `.env.suite.example` to uncomment the example URL (placeholder credentials
  only; never a real password).

## Decisions & findings

- **Installed version comes from the sibling `/machine/health` `version`** (NENE2#1414), cached in the
  control DB — not the static `catalog/apps.json` (values are live). Origin unconfigured / version
  unreported → `unknown` (defensive, never fabricated).
- **The upgrade apply is deployment-driven, not a runtime self-apply.** A running web app cannot
  atomically redeploy/restart itself; in Tier B the deployment swap is Suite's (compose), and the
  sibling's part is its boot-time migration (ADR 0014). This keeps ADR 0013 §3/§8 intact (Suite
  orchestrates, the sibling applies its own) while fixing the mechanism. → **ADR 0019 supersedes 0018.**
- **NENE2 stays Suite-agnostic.** Litmus test (from the NENE2 maintainer): "would NENE2 add this to
  core even if Suite didn't exist?" — YES for version reporting (#1414), NO for apply/orchestration.
  Audit: zero code/config coupling. Principle recorded.

## Issues & fixes

- **ADR 0018 mis-specified the apply mechanism** (sibling runtime `POST /machine/update`). Caught on
  review (a running app can't redeploy itself; the deploy swap is the orchestrator's). Corrected via
  ADR 0019 (deployment-driven) + withdrew NENE2#1416. Lesson: validate the apply/deployment model
  before contracting it (the same verify-against-ADR discipline, applied to a mechanism this time).
- **Our NENE2 issue wording seeded "suite/orchestrator" prose into the framework** (#1414
  PHPDoc/CHANGELOG). Fixed on the NENE2 side (NENE2#1417/#1418); going-forward principle recorded —
  request only generic framework features, never name/allude to Suite.

  removed locally and from the remote.

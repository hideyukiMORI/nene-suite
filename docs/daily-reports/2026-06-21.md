## Decisions

- **Product = two editions.** Self-hosted OSS (`docker compose up`, no ads, the
  operator owns everything; paid install support + bespoke development are the
  business) **plus** hosted **NeNe Cloud Free** (`free.nene-suite.com`,
  multi-organization, ad-supported, continued real use OK).
- **Run it as a business — committed.** The owner is operating the hosted service
  (accepting ongoing backup/DR, 個人情報保護法 安全管理措置, availability, support,
  abuse handling). The earlier "demo + disclaimer + shared org" framing was
  rejected: for financial data, cross-company exposure is a reputational failure
  no disclaimer survives.
- **Headline = anti-lock-in, not "free".** Canonical taglines adopted (recorded in
  `product-vision.md` and ADR 0015 §1.1): *「無料で始める。必要になったら、いつでも
  自社サーバーへ。」「データはあなたのもの。」* The exit (export → self-host) is the
  funnel, not churn.
- **Naming.** `free.nene-suite.com` (NeNe Cloud Free), `demo.nene-suite.com`
  (no-signup sample, reset), `app.nene-suite.com` (future paid). Start with `free`.
- **Legal review is batched** — one consolidated 西村法律事務所 re-review before
  public launch, not a per-change checkpoint (so development is not stalled).
- **Ads are house-ads only** (ADR 0013) — never targeted on tenant data.

## Key finding (changed the plan)

The sibling apps are **already multi-tenant from the foundation** — the Suite is
not. NeNe Invoice (ADR 0006), NeNe Records (reference impl), NeNe Payout
(ADR 0004/0018), NeNe Corpus (ADR 0005), NeNe Contact (ADR 0006), NeNe Serve
(ADR 0006) all carry `organization_id` on every tenant table, per-request
organization resolution (`single`/`path`/`subdomain`/`custom_domain`), SQL-level
isolation, and a cross-tenant `superadmin` role. So "single organization" is only
the apps' default resolution mode; the gap — and the remaining work — is the Suite
identity/registry layer (today a flat `operators` table; JWT carries only
`sub` + `suite_id`). The hardest part of a SaaS (tenant-isolated financial data)
is already built and reviewed.

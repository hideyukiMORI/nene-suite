## Decisions & findings

- **Post-install DB legitimacy is the app's judgement; the suite orchestrates + records.** Only the app
  knows its schema/identity/tenancy, so a generic read-only **preflight** on the sibling returns a
  verdict; the suite gates + audits, never inspects the database (preserves one-way Suite→NENE2).
- **Preflight is opt-in per app.** `/machine/database/preflight` is registered only when an app wires
  its `DatabaseCandidateInspector` — so each managed sibling must adopt it before the suite can
  preflight it; an unadopted app is the OQ4 refuse-by-default case.
- **The "apply" must be deployment-driven, not a runtime app endpoint.** NENE2's C (token) framing
  assumed a runtime "apply presents token → app re-verifies" handshake. A running app cannot safely
  re-point its own live connection — exactly the pattern withdrawn as NENE2#1416 (cf. ADR 0019). So
  apply = a deployer rewrites the env + recreates the container, and the app re-verifies the
  `token` + `fingerprint` **at boot, before migrating**. C is therefore deferred until the apply slice
  exists (no consumer-less signed token).
- **OQ resolutions (ADR 0023):** candidate env `NENE_SUITE_APP_{SNAKE}_DB_CANDIDATE_*`; token = per-app
  HMAC (machine key), not federation JWKS (wrong direction); tenant = `org_external_id`
  (single-tenant OSS = `not_applicable`); unsupported app = refuse-by-default + audited override;
  **read-only first** (read surface + preflight before the write/apply slice).
